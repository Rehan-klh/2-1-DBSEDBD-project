- Room capacity must never be exceeded.
- Allocation/transfer/release operations must preserve consistency.
- Approved room-change requests must safely update allocation.
- Use database transactions for multi-step allocation operations.

CORE WORKFLOWS
--------------
1. LOGIN
Student/Admin submits email, password, selected role.
Backend verifies credentials and actual role.
Return JWT.

2. STUDENT ROOM SELECTION
Student views available rooms.
Student selects an available room.
Backend checks:
- authenticated student
- room exists
- capacity available
- student does not already have ACTIVE allocation
Then create ACTIVE allocation.

No admin approval is required for initial selection.

3. ADMIN ROOM MANAGEMENT
Admin can:
- create rooms
- set capacity
- allocate students
- remove allocations
- transfer students
- directly override/change a student's room

4. ROOM CHANGE REQUEST
Student:
current room -> requested room + reason -> PENDING

Admin:
APPROVED or REJECTED

On approval, update the active allocation safely and enforce capacity.

5. LEAVE
Student submits request -> PENDING.
Admin can approve/reject/change status.
Student can view status.

6. COMPLAINTS
Student submits complaint -> PENDING.
Admin can move:
PENDING -> IN_PROGRESS -> RESOLVED
and add admin response.

7. VISITORS
Student submits visitor request -> PENDING.
Admin approves/rejects.

8. MESS
Student views menu.
Admin manages menu.
Student submits mess feedback.
Admin views feedback.

9. FEES
Admin manages fee records/status.
Student views own fees.
No real payment gateway.

10. ANNOUNCEMENTS
Admin creates/updates/deletes.
Students view.

11. NOTIFICATIONS
Create appropriate notification documents for important events where practical.
Students/Admins can view their own notifications and mark them read.

12. ACTIVITY LOGS
Record important administrative/system actions in MongoDB.
